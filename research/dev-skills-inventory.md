# Which recurring ways of working should become dev skills?

Research for [issue #22](https://github.com/luizvilla/Theia/issues/22) (dev map [#17](https://github.com/luizvilla/Theia/issues/17)), 2026-11-24. It feeds [#27](https://github.com/luizvilla/Theia/issues/27), "Choose which dev skills to write", where Luiz decides.

A **dev skill** (GLOSSARY.md) is a skill for the agents that build OwnStudio, kept in the repository's `.claude/skills/<name>/SKILL.md`, with a pointer in `AGENTS.md` so Codex finds it too. It is not a **setup skill** (slice 4, shipped to users).

Transcript counts below are **Bash tool calls whose command matches a pattern**, summed over the seven sessions (sessions are named by date). They measure how often a way of working recurred, not how often it went wrong.

**Two facts frame everything below.**
1. The repository has **no `AGENTS.md`, `CLAUDE.md` or `.claude/`** at its root. Every rule today lives in the session memory (private to Claude, invisible to Codex) or inside `plan.md`'s Rules sections. Codex built U8–U15 (memory, 2026-11-12) with no repository-level instructions to read. The first job of #27 is therefore a short root `AGENTS.md` (+ a `CLAUDE.md` that points to it), whatever skills are chosen.
2. The memory notes have grown into a run-book: the step-5 note alone carries about twenty "how to" lessons (env vars, Monaco, quick picks, pkill). That is exactly the material skills are for: loaded when needed, not pushed into every context.

### Summary of verdicts

- **New dev skills (5):** `ownstudio-run-app`, `ownstudio-drive-app`, `ownstudio-trial-intake`, `ownstudio-nine-steps`, `ownstudio-report`, plus a small `ownstudio-bench` procedure skill behind the AGENTS.md rules (6 if counted).
- **Extend an existing skill (3):** grilling round (`grilling` + `domain-modeling`), session resume (`wayfinder` + `handoff`), dev map (`wayfinder`, via the map's Notes).
- **Already covered (2):** commit plan (`to-spec`/`to-tickets`/`implement` + the map), retro (`retro`).
- **Rules, not skills:** window check, Twist build paths, local-only, quiet machine, `/proc`.

A sensible first batch for #27 is **`AGENTS.md` + `ownstudio-run-app` + `ownstudio-drive-app` + `ownstudio-bench`**: they carry the safety rules and the most-repeated mechanics, and the nine-step run and the trial intake build on them.

## Rules that belong in CLAUDE.md / AGENTS.md rather than a skill

These must hold in every session, or are one-liners that do not justify a skill's trigger. Per Matt's `retro` and `writing-for-agents`, the file stays short and mostly points elsewhere.

1. **Power:** never switch the converter on (no write to `Converter/Mode` that powers it, no power procedure) unless Luiz says in this session he is at the bench; one run at a time; read `Converter/Mode` after every power run. Automated tests and agents never set the power mode. Details: `ownstudio-bench`.
2. **Processes:** stop only the processes you started (binary path + debug port). No broad `pkill`; never `pkill -f`/`pgrep -f` a pattern that appears in your own command line (use `[b]racket` patterns).
3. **Shell state:** env exports do not persist between tool calls: set app env vars in the same call that starts the app.
4. **Where to work:** build and test under `/data/ownstudio` (the home disk is nearly full); throwaway profiles and homes under `/data/ownstudio/build`; never touch `~/OwnStudio` or an earlier trial folder.
5. **Tools:** PlatformIO is `~/.platformio/penv/bin/pio` (not `/usr/bin/pio`); the app's Python is `app/python/.venv`, the mission's `/data/ownstudio/build/venv-mission`.
6. **Every commit** builds and passes its tests; a commit that changes the window reruns `shots.mjs`, `navigation-test.mjs` and `menus-test.mjs` (see `tools/storyboard-shots/README.md`).
7. **Public repo:** no emails, no third-party names beyond the docs, nothing sensitive. Storyboards, checklists and F14 shots stay local (`.git/info/exclude`). Third-party forks (Pulsim) are not pushed without Luiz's OK.
8. **Pushing and issues:** pushing to `luizvilla/Theia` and `luizvilla/examples` is allowed; issues go to `luizvilla/Theia`; no pull request unless asked.
9. **Status lives on the dev map** (issue #17): claim a ticket by assigning and commenting, reference it as `Refs #n` in commits; plan.md holds rationale only (Q199).
10. **Machine care:** no heavy `/proc` scans; check load before timing gates.
11. **Vocabulary:** read `GLOSSARY.md`; Luiz says "feeder", write APS; say "dev skill" or "setup skill", never "skill" alone.
12. **Pointer list:** one line per dev skill, so Codex (which does not load `.claude/skills/` by itself) knows to open the file.

## Open points for #27

- **Codex and skills.** This research did not verify how the Codex version in use loads skills; the safe assumption is an `AGENTS.md` pointer list with paths, as #22 states.
- **Where the gotchas live.** Putting the Theia-driving gotchas in `tools/storyboard-shots/README.md` keeps them next to the code they explain; the skill then only triggers and points. That is the leaner choice.
- **Memory slimming.** Once these skills and `AGENTS.md` exist, the memory notes can drop their run-book parts and keep only project state.
- **Scratchpad scripts.** The gate runner and F14 `env.sh` lived in a session scratchpad and one was lost; any dev skill that needs a script should get it committed under `tools/`.
